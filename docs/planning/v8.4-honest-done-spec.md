## §2 — Doctrine (three structural properties)

1. **The model cannot write the ledger.** No tool exposes `task_gates`; the only writers are `declareGates` (INSERT OR IGNORE — additions only, no update/delete API for a criterion) and `recordGateResult` (harness evidence). unlazy's own `GATES.md` is model-editable; that hole is closed.
2. **Checked-without-evidence is unmet.** `recordGateResult` refuses `met` without evidence; `ledgerVerdict` counts such a row as pending.
3. **Surrender is visible.** A gate that cannot be met is `abandoned` with a reason — parsed from the model's final report (`ABANDON: <id> <reason>`, the one thing the model may say about a gate) — and every consumer lists abandoned gates. Silent scope-narrowing is the failure; visible surrender is honest.

## §3 — Data model

`task_gates` (`src/lib/v8-4/schema.ts`, `ensureV84Tables` at boot): `(task_id, gate_id) PK · criterion · check_kind ∈ {shell, landing, manual} · check_cmd · expect · state ∈ {pending, met, failed, abandoned} · evidence · abandon_reason · source ∈ {submission, ritual, plan, harness} · frozen_at · checked_at · created_at`.

`scheduled_tasks.gates TEXT` (JSON `GateSpec[]`, additive column probe in `ensureScheduledTasksTable`).

`GateSpec = { id?, criterion, check?, expect?, kind? }` — `expect` is a substring or `/regex/flags`; absent ⇒ exit code 0 decides.

## §4 — Where gates come from (rule zero: before the work)

| Source       | Seam                                                                                                                                                                      | Author                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `submission` | `TaskSubmission.gates` → `submitTask` declares right after the tasks INSERT                                                                                               | API/operator/harness callers         |
| `ritual`     | `scheduled_tasks.gates` → both submit paths + retry pass `gates` + `gatesSource:"ritual"`                                                                                 | operator (`mc-ctl gates set-ritual`) |
| `plan`       | planner object-form criteria `{criterion, check, expect}` → `goal.metadata.gates` → orchestrator declares after PLAN (Prometheus) / swarm passes to each child submission | planner LLM                          |
| `harness`    | `G-landing` declared at completion for nanoclaw non-messaging tasks                                                                                                       | code                                 |

At run start the dispatcher **freezes** the ledger (`frozen_at`) and renders it into the runner's description (`renderGatesBlock`) — only for tasks WITH gates; ungated traffic's prompt is byte-for-byte unchanged.

## §5 — Modes and the consumer (`src/lib/v8-4/consumer.ts`)

`TASK_GATES_MODE`: `off` (default) · `shadow` · `enforce`. Unknown ⇒ `off`.

- **off** — declare/freeze/render only; nothing runs.
- **shadow** — `evaluateLedger` runs the runnable gates at completion; verdict on `tasks.output.gates` + trace `gates.evaluated`; status untouched.
- **enforce** — additionally: verdict `failed` demotes `completed → completed_with_concerns`; the ledger block (`Gates: n/N met · FAILED: … · unverified: … · ABANDONED: …`) is appended to the deliverable; ABANDON lines honored.

Verdicts: `met` (all met-with-evidence / abandoned) · `failed` (≥1 failed check) · `unverified` (something pending — manual gates, landing with no claim) · `none`. A failed task is never promoted by a met ledger.

## §6 — The gate-check runner (`src/lib/v8-4/gate-check.ts`)

Port of unlazy's `gate-check.mjs`: `/bin/sh -c` in its own process group, **minimal env** (PATH/HOME/LANG/TZ + `MC_TASK_ID`=the task — never the service env), default timeout 60s (`TASK_GATES_CHECK_TIMEOUT_MS`, validated), whole-ledger wall-clock budget 120s (`TASK_GATES_LEDGER_BUDGET_MS`; gates past it stay pending, never FAILED), group-kill on timeout, output cap 256KB, evidence = deciding tail (≤400 chars, **secret-redacted**). EXPECT decides over exit code; regex EXPECTs run inside a `vm` context with a 250ms deadline on the last 64KB of output and nested-quantifier patterns are rejected outright (a pathological pattern cannot wedge the event loop — qa C2). **Every check command passes `validateShellCommand`, the same guard as `shell_exec`** (deny-list, `$(…)`/process substitution, secret-file reads, primary-checkout git mutation, unscoped vitest) before it spawns — a plan-authored gate never widens the envelope the model already has (qa C1). Manual gates are never flipped by the harness. **Shell gates are skipped (left pending, counted `shell_skipped`) for tasks that ran in a container** (nanoclaw; heavy when containerized): the host tree is not the tree the work touched, so a host-side `tsc` would be a manufactured green (qa W1) — the landing gate is the container task's proof. Landing gates call `probeLanding` (`landing.ts`): `git ls-remote --heads origin`, explicit `PR #N`/`pull/N` via `gh pr view`, commit claims (only after the word commit/sha/pushed; UUID first blocks excluded) via `git branch -r --contains` after a fetch — `true` (met, only when EVERY claim verifies) · `false` (failed) · `null` (no claim → stays unverified).

## §9 — Numbers-provenance audit (`src/lib/v8-4/numbers.ts`)

`ToolRegistry.execute` records a digest of every tool result of the current run (task id from `runToolContext`, ≤8KB/item, ≤256KB/task, freed on every dispatcher exit path). At completion the consumer audits aggregate-looking numbers in the deliverable against that corpus + the task's own input → trace `numbers.audited {found, unverified}` + `output.numbers_audit`. Footer `⚠️ Cifras sin respaldo…` only when `TASK_GATES_NUMBERS_ANNOTATE=true`. Never rewrites a number, never blocks.

## §12 — Boundaries / residuals

- Container workers (nanoclaw/heavy in Docker) do not see host env flags; the wall is host-only. Their ledger is still evaluated on the host at completion (that IS the landing check).
- Plan-declared gates that appear mid-run (Prometheus after PLAN) are consumed by the dispatcher at completion, not by the wall (the hook is attached at query start).
- Manual gates are only ever `pending` → `unverified` until V9 W1's capable-tier `criteria_check` consumes them (`verifier.ts` should read `task_gates` as its `checks[]` input).
- Checks run in the service cwd; use absolute paths in check commands.
- The numbers regex is heuristic (identifiers/years/times excluded); treat `numbers.audited` as a trend metric, not a verdict.
- **Dormant footprint (qa W4, intentional):** even with `TASK_GATES_MODE=off`, tool-using tasks and scheduled tasks get `tasks.output.numbers_audit` + one `numbers.audited` trace row (the 8.4.4 shadow metric), and every dispatch runs one `listGates` query. Not user-visible; ungated prompts and SDK options are byte-for-byte unchanged.
- Container-blob `success` must be a **boolean** to count as self-attestation (`null` ⇒ concerns, qa I2).

## §15 — Settleable `expect` (2026-09-12)

**Origin:** YOINK review (DefiLeoo/YOINK — "a claim that cannot be graded is refused the moment it is written"). Plan: `docs/planning/gate-settleable-expect-plan.md`.

**The hole, measured read-only on the live ledger 2026-09-12:** `expect` was a free substring or `/regex/` and the planner prompt said so. Of the 61 predicate-bearing rows written since 2026-08-17, 34 used a digit-only regex (`/[0-9]/`, `/[1-9]/`, `/[3-9]/`, `/[4-9]|1[0-9]/`, `/^[1-9][0-9]*$/m`, `/.*/`) or the bare substring `0`. `grep -c 'MODEL OUTPUT' …` + `/[0-9]/` is MET by the failure output `0`; five such plan rows were recorded MET in enforce mode, and 12 nightly ritual `COUNT(*)` rows passed on any positive count. `isLiteralSourcedCheck` (§7) closed the sibling hole on the `check` side; nothing checked the `expect` side.

**Grammar** (`src/lib/v8-4/expect.ts`, allow-by-membership):

| form | evaluation |
|---|---|
| `gte N · gt N · lte N · lt N · eq N · neq N · between A B` | the LAST non-empty line of the check output must be a bare number; compared numerically. A non-numeric last line FAILS the gate with evidence `last line is not a number — …` (never a pass, never a skip). |
| `/regex/flags` | unchanged (vm-sandboxed test on the 64 KB tail window), but must name at least one literal non-digit character. |
| anything else | substring on the tail window, unchanged. |

**Write-time refusal** (`isUnsettleableExpect`): digit-only regex (`regexNamesALiteral` strips digit classes, `\d`, anchors, groups, alternation, quantifiers, `.`, whitespace classes; nothing left ⇒ refused) · regex/substring satisfied by the failure outputs `""` or `"0"` · a comparator word without a valid number (`gte ten`, `between 3`) · `between` with low > high · a regex that does not compile. Blank `expect` still means "exit code decides". Every refusal names the rule and the fix.

**Wiring:** `parseGateSpecs` (API `POST /tasks`, `mc-ctl gates set-ritual` via `scripts/gates-validate.ts`, `rituals/dynamic.ts` create) **throws** with the reason → HTTP 400 / CLI error. `gateSpecsFromGoal` (Prometheus plan gates) declares the row **ABANDONED** with `abandon_reason: expect cannot fail — …`, the same visible surrender as a literal check (doctrine 3); abandoned rows never pass and never demote. Already-declared rows are evaluated exactly as before (read path unchanged) — the rule is enforced at declaration, not retroactively. Counter `mc_gate_refusals_total{source=plan|spec, reason=literal_check|unsettleable_expect}` (`src/lib/v8-4/gate-metrics.ts`).

**Producers told, not just policed:** `src/prometheus/planner.ts` prompt now states the grammar and the rule ("for a count use gt 0 / gte N and print the number last; a /regex/ must name a word; `/[0-9]/` is refused"). Ritual gates are operator-authored JSON (no LLM surface) and hit the same validator.

**Corpus replay** (`npx tsx scripts/replay-gate-expects.ts data/mc.db`, read-only) is the pre-ship gate for any change to the rule: on 2026-09-12 it refused exactly the 34 digit-only/`0` rows and kept all 27 word-naming or value-naming expects (`200`, `Plan de Acción`, `/[0-9a-f]{7}/`, `/Avg Δ/`, `/v\d+/`, `/EXISTS|MISSING/`…). An unexpected refusal means the rule is wrong, not the row.

**Stored payloads (qa R1 C1):** `rituals/dynamic.ts scheduleGates` re-parses a schedule's `gates` column on every run and swallows parse errors into "running ungated". A refusal there would have silently deleted the only live ritual gate (schedule `9e06a237…` "MexicoNecesario — Tweet Diario", `expect /^[1-9][0-9]*$/m`, 20 rows, the gate that catches a day with no tweet). Fold: `parseGateSpecs(raw, { onUnsettleableExpect: "abandon" })` keeps the gate as an ABANDONED spec (no metric tick — it would count the same stale row nightly); the ritual runs with a visible surrender until the operator re-sets the gate. **Operator step:** `./mc-ctl gates set-ritual 9e06a237-a13d-47fe-99a1-a903005429a2 docs/planning/gates/mexiconecesario-tweet-diario.gates.json` (same check, `expect: gt 0`; `mc-ctl db` prints `-header -column`, so the count is the last line).

**Structural floor (qa R1 C-R2):** `declareGates` itself abandons a shell spec whose expect cannot fail (`source=declare` on the counter) — a fourth producer that skips validation cannot land a pending → MET row.

**Grammar folds (qa R1 lens A):** `regexNamesALiteral` also strips group prefixes (`(?:` `(?=` `(?!` `(?<=` `(?<!` `(?<n>`), negated and escape-only classes (`[^0-9]`, `[^\d]`, `[\s]`) and `\D \n \r \t`; failure outputs are what the runner hands over (`"0\n"`, `"\n"`, `" 0\n"`, `"0\r\n"` as well as `""`/`"0"`); the write-time probe runs through the vm-sandboxed `safeRegexTest` (moved into `expect.ts`; a 420-char alternation bomb returns bounded); nested-quantifier patterns, regex look-alikes with surrounding whitespace or uppercase flags, no-space comparator typos (`gte5`) and >500-char expects on the plan path are refused rather than silently becoming never-matching substrings. Evidence marker is `not a number: ` (14 chars of the 80-char `mc-ctl gates` readout). **R2 folds:** a comparator that 0 and any count both satisfy (`gte 0`, `gt -1`, `neq -1`) is refused; the digit-only refusal message no longer claims anchored forms pass on any count (they grade a stray digit in noise, e.g. the `1` in `sh: 1: not found`) — R2 verified the live `/^[1-9][0-9]*$/m` gate had 0 false METs in 30 days, so the migration to `gt 0` is a precision gain, not a bug fix. R2 fuzz: 1,415 random compilable patterns, 0 regex bypasses (probe and matcher share `safeRegexTest` + the same failure set, so admitted ⟹ never MET on `0\n`).

**Residuals (queued, not fixed):** a labelled count such as `/n: [0-9]+/` names a literal and passes the probe (0 live instances) · the 256 KB output cap keeps the HEAD, so a comparator whose check prints >256 KB before the number FAILS (evidence says so) · a trailing stderr line after the number FAILS the comparator (evidence says so; the prompt tells the planner to redirect) · a ledger whose ONLY gates were refused reports `met` with `met: 0` (pre-existing `ledgerVerdict` semantics, now pinned; operator decision whether that should be `unverified`) · `schedule_task` exposes no `gates` parameter, so `createSchedule`'s gates write path has no caller — ritual gates are CLI-only.

**Tests:** `expect.test.ts` (grammar, live refused/kept tables incl. the lens-A bypass families, sandbox bound, mutation pin `/[0-9]/` refused at write time + `gt 0` fails on `0` at check time), `gates.test.ts` (spec path throws, plan path abandons incl. oversize, the row lands `abandoned`, verdict-level pins, declareGates floor, counter ticks at the doors and not on a stored re-parse), `gate-check.test.ts` (comparator evaluation, non-numeric evidence, legacy row inserted by SQL still evaluates), `dynamic-gates.test.ts` (the live tweet-ritual payload comes back abandoned, a malformed column still degrades to ungated).
